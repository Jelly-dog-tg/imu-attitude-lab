# C++ 性能与稳定性实测

本文记录 `cpp/` 模块的实测数据与结论。所有数字都可用仓库内的基准程序复现，
不是估算值。**当前数字采集于 Windows 11 + MinGW-w64 GCC 11.2，16 逻辑核**；
Linux/glibc 的对照数据由 CI 的 `cpp-stability` 任务产出，两者差异在文末讨论。

## 如何复现

```bash
cpp/scripts/build.sh Release          # 配置 + 构建（-Werror 生效）
cpp/scripts/run_tests.sh              # 单测 + 稳定性 + 队列基准

# 只跑基准
cpp/build/bin/imu_lab_bench       --frames 500000 --sweep --queue-capacity 4096 --anomaly-rate 0.02
cpp/build/bin/imu_lab_bench_queue --items 1000000
```

## 1. 端到端流水线：功能正确性

50 万帧、2% 注入异常帧、1/2/4 个解析线程各跑一遍：

| workers | frames | rejected | wall ms | frames/s | maxQ | end2end mean ms | RSS Δ KB |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 500000 | 10054 | 538.4 | 928695 | 302 | 0.012 | 236 |
| 2 | 500000 | 10054 | 1277.9 | 391259 | 173 | 0.010 | 112 |
| 4 | 500000 | 10054 | 5187.7 | 96381 | 892 | 0.025 | 272 |

三点结论：

1. **完整性成立**：三种线程数下 `rejected` 完全相同（10054），
   `lost frames = 0`，`pitch` 统计量逐位一致。基准程序把这条不变量做成断言，
   CI 里任何一次丢帧都会让任务失败。这正是多线程数据处理最该保证的性质：
   **线程数只影响速度，绝不影响结果**。
2. **异常帧比例可控**：注入 2%，实测 `10054 / 500000 = 2.01%`，
   说明"异常帧比例"这个指标是真实可用的，而不是摆设。
3. **本平台的吞吐随线程数下降**，这一点必须解释清楚，见第 3 节。

## 2. 队列微观基准：定位瓶颈

把队列单独拿出来测，才能判断性能问题出在流水线设计还是队列本身：

| 配置 | elapsed | items/s |
|---|---:|---:|
| 同线程 push+try_pop（无争用下限） | 5.5 ms | 182,010,122 |
| 1 生产者 / 1 消费者 | 41.6 ms | 24,062,698 |
| 1 生产者 / 2 消费者 | 55.1 ms | 18,160,785 |
| 1 生产者 / 4 消费者 | 415.7 ms | 2,405,768 |
| 1 生产者 / 8 消费者 | 5156.2 ms | 193,943 |

无争用时每秒 1.8 亿次操作；一旦有 8 个线程阻塞在同一个条件变量上，
吞吐掉到 19 万次/秒——**三个数量级**。所以第 1 节的吞吐下降不是流水线逻辑写错，
而是队列的唤醒路径在这个平台上代价极高。

### 为此做的优化

最初 `push`/`pop` 无论有没有等待者都会调用一次 `notify_one()`。
在 MinGW-w64 的 winpthreads 实现里，`notify_one()` **即使没有任何等待者也要陷入内核**。
改为用等待者计数（`waiting_not_empty_` / `waiting_not_full_`，在持锁时读取）
只在确实有人等待时才唤醒：

| 场景 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 同线程 push+try_pop | 119.6M ops/s | 182.0M ops/s | +52% |
| 1 生产者 / 1 消费者 | 19.6M items/s | 24.1M items/s | +23% |

计数器在持锁状态下读取、解锁后才发信号，中间到达的消费者会直接看到新元素
而不是进入等待，因此不存在丢唤醒窗口；`close()` 仍然无条件 `notify_all()`，
关闭路径上绝不省这一次唤醒。

## 3. 为什么本平台上线程越多越慢

解析一帧的实测成本是 **0.0003 ms（约 300 ns）**——纯字符串切分和数值解析。
也就是说这条流水线在当前工作负载下**完全是同步开销主导，而不是 CPU 主导**。
给一个同步受限的流水线加线程，只是增加互斥量争用，必然变慢。

这是测量结论，不是设计缺陷：真实负载（CSV 解码、滤波、更复杂的校验）会让
worker 真正占用 CPU，那时多线程才会开始收益。

给后续优化的方向（已记录，未实现）：

- **批量交接**：队列按 K 帧一批 push/pop，把锁与唤醒开销摊薄 K 倍。
  这是真实采集前端的标准做法（环形缓冲区 + 块交接）。
- **无锁环形缓冲**：用原子序号 + CAS 做单生产者/多消费者的 ring buffer，
  彻底移除互斥量。
- **自适应等待**：短路路径下先自旋若干次再进入条件变量等待。

### 平台差异

`std::mutex` + `std::condition_variable` 的争用代价是平台相关的：
glibc 用 futex，争用时先自旋再陷入内核；winpthreads 在争用时基本直接走内核。
因此同一份代码在 Linux 上的扩展性预期明显好于 Windows。
CI 中的 `cpp-stability` 任务会在 Ubuntu 上跑 `imu_lab_bench_queue` 并打印结果，
**Linux 的真实数字以 CI 日志为准**，本文不做没有依据的推断。

## 4. Python 与 C++ 的实现对比

同一份 10 万行 CSV，两个实现都做完整的读取 + 校验 + 统计 + 跳变检测：

| 实现 | wall ms |
|---|---:|
| `python -m host.analyze` | 2695 |
| `imu_lab_cli analyze` | 1193 |

约 2.3 倍（含进程启动）。这里的价值不是"跑得快"，而是
**两个实现共享同一 CSV schema、同一套判定规则**：`raw_line` 含逗号需要引号、
`x`/`y` 必须成对、`elapsed_s` 非负、跳变阈值严格大于——这些约束在两侧都有单测，
CI 里还有双向互操作任务（C++ 写、Python 读；Python 写、C++ 读）实际跑一遍。

## 5. 内存

`imu_lab_cli stream` 用 `GetProcessMemoryInfo`（Windows）或 `/proc/self/statm`
（Linux）采样 RSS，输出 `RSS start / end / peak`。50 万帧运行中增量在
112–272 KB 区间，说明流水线是**流式**的：不缓存整段数据，
内存占用与帧数无关，只与队列容量和线程数有关。

`--json` 输出的 `rss_peak_bytes` 可直接被监控脚本消费。

## 6. 稳定性检查清单

`cpp/scripts/run_tests.sh` 与 CI 覆盖以下不变量：

- 任意线程数下 `received == parsed + rejected == logged`，`lost_frames == 0`；
- 任意线程数下 `pitch`/`roll` 的均值与标准差逐位一致（顺序无关的可复现性）；
- 队列水位不超过配置容量；
- 容量为 1 的极端背压下不丢帧（`SurvivesAnExtremelySmallQueue`）；
- 阻塞的生产者/消费者在 `close()` 后必定被唤醒（不出现关机死锁）；
- 4 生产者 × 3 消费者并发压测 8000 条，校验和精确匹配（无丢失、无重复）；
- ASan+UBSan 与 TSan 两套 sanitizer 下跑全部单测（CI `cpp-sanitizers`）。
